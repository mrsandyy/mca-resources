# Unit 3: Addresses and Binding

### Memory Management

**Memory Management** is a core function of an operating system (OS) that controls and coordinates the computer's main memory (RAM). It is responsible for the dynamic allocation and deallocation of memory space to running programs (processes). Its primary goal is to manage memory resources efficiently, ensure processes are isolated and protected from each other, and translate logical program addresses into physical hardware addresses.



A fundamental concept in memory management is the separation of the address space seen by the program from the actual physical addresses in the hardware.

### Logical vs. Physical Addresses

- **Logical Address (or Virtual Address):** This is the address generated by the **CPU**. It's the address that your program *thinks* it's using. When you write a C program and use a pointer, that pointer holds a logical address. This address space starts from 0 and goes up to the maximum address the CPU architecture supports (e.g., $2^{64}$ on a 64-bit system). The set of all logical addresses generated by a program forms the **logical address space**.

- **Physical Address:** This is the *actual* address in the **Main Memory (RAM)**. It's the address that the memory hardware sees. This address space is determined by the amount of RAM you have installed (e.g., 0 to 16GB). The set of all possible physical addresses forms the **physical address space**.

- **Memory Management Unit (MMU):** This is a hardware component (usually on the CPU chip) that **translates logical addresses into physical addresses** at run-time. This translation is the core of memory management.

In compile-time and load-time binding, the logical and physical addresses are the same. In **execution-time binding**, they differ.

### Address Binding

Address binding is the process of mapping a logical address to a physical address. This can happen at three different stages:

1. **Compile Time:**
   
   - If the exact physical memory location where the process will reside is known *before* the program is compiled, the compiler can generate **absolute code**.
   
   - **Example:** In an old, simple system, the OS might always live at address 0 and the first user program at address 1000. The compiler would bind all program addresses to start at 1000.
   
   - **Drawback:** Extremely inflexible. If the location changes, the code must be **recompiled**.

2. **Load Time:**
   
   - If the memory location is *not* known at compile time, the compiler generates **relocatable code**. This code uses addresses relative to the start of the program (e.g., "100 bytes from the beginning").
   
   - When the program is **loaded** into memory, the loader (part of the OS) determines the starting physical address and *adds* this base address to all the relocatable addresses to create the final physical addresses.
   
   - **Drawback:** The program cannot be moved in memory *after* it has been loaded.

3. **Execution Time (Run Time):**
   
   - This is the most flexible and modern approach. Binding is delayed until the program is actually running. This requires hardware support, such as **base and limit registers**.
   
   - When the CPU generates a logical address, the **MMU** translates it to a physical address *at that moment*.
   
   - **Benefit:** This allows the OS to **move a process's memory** from one location to another *while it is running*. This is essential for features like swapping, paging, and compaction. All modern general-purpose OSes (like Linux, Windows, macOS) use execution-time binding.

## 2. Dynamic Loading and Linking

These are techniques to save memory and time by only loading code when it's needed.

- **Dynamic Loading:**
  
  - **Concept:** A routine (like a function or module) is not loaded into memory until it is **called** for the first time.
  
  - **Process:** The main program loads first. When it calls a routine, the program checks if the routine is already loaded. If not, the loader is called to load the routine from disk into memory, update the program's address tables, and then execute the routine.
  
  - **Benefit:** Saves memory. Routines that are rarely used (like complex error-handling code) don't take up space in RAM unless they are actually needed. This also leads to faster program startup.

- **Dynamic Linking:**
  
  - This concept applies to **library code** (e.g., `printf()` in C, which lives in `libc`).
  
  - **Static Linking:** The *old* way. The linker (a build tool) *copies* the code for all library functions used (like `printf()`) directly into your final executable file (e.g., your `.exe` or `a.out`).
    
    - *Pro:* The executable is self-contained.
    
    - *Con:* Massive executables (every program has its own copy of `printf()`) and wastes RAM (if 10 programs are running, there are 10 copies of `printf()` in memory).
  
  - **Dynamic Linking:** The *modern* way. The executable does *not* contain the library code. Instead, it contains a small piece of code called a **stub**.
    
    1. When your program calls `printf()`, it actually calls the stub.
    
    2. The stub checks if the shared library (`libc.so` on Linux, `msvcrt.dll` on Windows) is already loaded into memory for *any* process.
    
    3. If not, the OS loads the library into memory.
    
    4. The stub then patches itself to point directly to the `printf()` function in that shared library and jumps to it.
    - **Benefit:** **Huge memory savings**. Only *one copy* of `printf()` exists in RAM, shared by all running programs. Also, libraries can be updated (e.g., for a security patch) without recompiling every program that uses them.

## 3. Contiguous Allocation

This is the simplest memory allocation method. The OS loads an entire process into one single, *unbroken* block of memory.

- **Protection:** Hardware support is used to protect processes from each other. A **relocation register** (or base register) holds the smallest physical address, and a **limit register** holds the range (size) of the process. Every logical address generated by the CPU is checked:
  
  1. Is `logical_address < limit_register`? If no, trap (addressing error).
  
  2. If yes, `physical_address = relocation_register + logical_address`.

- **Fixed-Partition Scheme:**
  
  - Memory is divided into **fixed-size partitions** (e.g., 1MB, 2MB, 4MB) when the system boots.
  
  - When a process arrives, it's placed in a partition that is large enough for it.
  
  - **Problem:** Causes **Internal Fragmentation**.

- **Variable-Partition Scheme (Dynamic Allocation):**
  
  - The OS keeps a table of free memory blocks (called "holes").
  
  - When a process arrives, the OS searches for a hole that is large enough.
  
  - The OS allocates *exactly* the memory the process needs from that hole, and the leftover portion becomes a new, smaller hole.
  
  - When a process finishes, its memory is returned and (potentially) merged with adjacent free holes.
  
  - **Problem:** How to choose a hole?
    
    - **First-Fit:** Allocate the *first* hole in the list that is large enough. Fast, but can leave small, useless holes.
    
    - **Best-Fit:** Allocate the *smallest* hole that is large enough. Must search the entire list. Tries to save large holes for large processes, but creates tiny, unusable leftover holes.
    
    - **Worst-Fit:** Allocate the *largest* hole. Also must search the entire list. The idea is that the leftover hole will be large enough to still be useful.
  
  - This scheme leads to **External Fragmentation**.

## 4. Fragmentation

Fragmentation is the problem of wasted memory that cannot be used.

### Internal Fragmentation

- **What is it?** Wasted memory *inside* an allocated block.

- **When does it happen?** When a process is given a block of memory that is **larger than it needs**.

- **Example 1 (Fixed Partition):** In a fixed-partition scheme, you have a 100KB partition. A 70KB process is loaded into it. The remaining **30KB is wasted** (internal fragmentation) because it belongs to that partition and cannot be given to any other process.

- **Example 2 (Paging):** For a process of 72,766 bytes and a page size of 2,048 bytes:
  
  - The process needs 35 pages plus 1,086 bytes.
  
  - It will be allocated 36 pages in total.
  
  - The last page (2,048 bytes) has 1,086 bytes used.
  
  - Internal fragmentation = 2,048 - 1,086 = **962 bytes** wasted in the last page.

### External Fragmentation

- **What is it?** Wasted memory *between* allocated blocks.

- **When does it happen?** In variable-partition schemes. Over time, memory becomes a set of small, non-contiguous free blocks.

- **Example:** You have 500KB of total free memory, but it's broken up into three holes: `[150KB hole]`, `[Process A]`, `[200KB hole]`, `[Process B]`, `[150KB hole]`.
  
  - A new process arrives that needs **300KB**.
  
  - Even though there is 500KB of total free space, **it cannot be loaded** because no single hole is large enough.

- **Solution:** **Compaction**. The OS periodically shifts all the allocated processes to one end of memory to gather all the small holes into one large free block. This is very time-consuming and requires execution-time address binding.

## 5. Paging

Paging is a non-contiguous memory allocation technique that **solves the external fragmentation problem**.

- **Core Idea:**
  
  1. Divide **Physical Memory (RAM)** into fixed-size blocks called **frames** (e.g., 4KB each).
  
  2. Divide **Logical Memory (Program)** into blocks of the *same* size called **pages** (also 4KB).

- **How it Works:**
  
  - When a program is to be executed, its pages can be loaded into **any** available frames in physical memory. The frames **do not need to be contiguous**.
  
  - The OS keeps a **Page Table** for *each* process. This table is a simple array that maps the program's logical pages to their corresponding physical frames in RAM.

- **Address Translation in Paging:**
  
  - The CPU generates a logical address, which is split into two parts:
    
    1. **Page Number (p):** Used as an **index** into the Page Table.
    
    2. **Page Offset (d):** The location *within* the page (e.g., from 0 to 4095).
  
  - **Translation Process:**
    
    1. The MMU extracts the page number `p`.
    
    2. It looks up entry `p` in the process's Page Table to get the **frame number (f)**.
    
    3. It combines the frame number `f` with the page offset `d` to create the final **physical address**.

- **Example:**
  
  - Logical Address: `10250` (and page size is 4KB = 4096)
  
  - Page Number (p) = `10250 / 4096 = 2`
  
  - Offset (d) = `10250 % 4096 = 2058`
  
  - The MMU looks at **Page 2** in the Page Table.
  
  - The Page Table says: "Page 2 is in **Frame 5**."
  
  - The MMU calculates the Physical Address = `(Frame 5 * 4096) + 2058 = 20480 + 2058 = 22538`.

- **Performance Issue & TLB:**
  
  - Since the page table is kept in main memory, every data access requires *two* memory accesses: one for the page table and one for the data.
  
  - **Solution:** A **Translation Look-aside Buffer (TLB)** is used. This is a special, fast, associative hardware cache.
  
  - When the CPU generates a logical address, the page number is checked against the TLB.
    
    - **TLB Hit:** (Page number is in the TLB) The frame number is retrieved instantly, and only one memory access is needed.
    
    - **TLB Miss:** (Page number is not in the TLB) The page table in main memory is accessed (first access), the frame number is found, and this mapping is added to the TLB. Then the data is accessed (second access).

- **Effective Access Time (EAT):** Let $\alpha$ = Hit Ratio, $\epsilon$ = TLB search time, and $t_{mm}$ = memory access time.
  
  - $EAT = (\text{Cost of Hit}) \times \alpha + (\text{Cost of Miss}) \times (1 - \alpha)$
  
  - $EAT = (t_{mm} + \epsilon) \times \alpha + (2 \times t_{mm} + \epsilon) \times (1 - \alpha)$
  
  - **Example:** With a 99% hit ratio ($\alpha=0.99$), 100ns memory access, and 20ns TLB search:
    $EAT = 0.99 \times (100 + 20) + 0.01 \times (2 \times 100 + 20) = 0.99 \times 120 + 0.01 \times 220 = 121ns$.

- **Memory Protection:**
  
  - Protection is implemented in the page table using a **valid-invalid bit**.
  
  - **valid (v):** The page is in the process's logical address space and is legal to access.
  
  - **invalid (i):** The page is *not* in the process's logical address space.
  
  - Any access to an invalid page results in a trap to the OS.

- **Shared Pages:**
  
  - Paging allows for efficient sharing of common code. One copy of read-only (**reentrant**) code, like text editors or compilers, can be shared among multiple processes.
  
  - Each process's page table simply points to the *same* physical frame for those shared pages.

- **Pros & Cons:**
  
  - **Pros:**
    
    - **Eliminates External Fragmentation.** Any free frame can be used.
    
    - Allows for code/data sharing.
  
  - **Cons:**
    
    - **Still has Internal Fragmentation,** but only in the *last* page of the process.
    
    - **Overhead:** Storing the Page Table itself takes up memory.

## 6. Segmentation

Segmentation is another non-contiguous method that views memory from a *programmer's* perspective.

- **Core Idea:** A program is *not* a single linear list of addresses. It's a collection of logical units called **segments**.
  
  - Example: A C program has a `code` segment, a `global variables` segment, a `heap` segment, and a `stack` segment.

- **How it Works:**
  
  - Each segment is a variable-length block of memory.
  
  - The OS keeps a **Segment Table** for *each* process.
  
  - Each entry in the table specifies:
    
    1. **Base:** The starting *physical address* of the segment.
    
    2. **Limit:** The *length* (size) of the segment.

- **Address Translation in Segmentation:**
  
  - A logical address is a two-part tuple: **<segment-number, offset>**.
  
  - **Translation Process:**
    
    1. The MMU uses the `segment-number` as an index into the Segment Table to get the `base` and `limit`.
    
    2. **Protection Check:** The MMU checks if the `offset < limit`.
       
       - If **No**, the address is invalid (outside the segment's bounds). This causes a trap to the OS (a "segmentation fault").
       
       - If **Yes**, the address is valid.
    
    3. The MMU calculates the Physical Address = `base + offset`.

- **Pros:**
  
  - Reflects the logical structure of a program.
  
  - Provides excellent protection (e.g., the `code` segment can be marked read-only).
  
  - Allows for easy sharing of segments (e.g., multiple processes can share the same code segment).

- **Cons:**
  
  - **Re-introduces External Fragmentation.** Because segments are variable-sized, loading and unloading them creates holes in memory, just like in the dynamic contiguous allocation scheme.

## 7. Virtual Memory

**Virtual Memory** is a powerful technique that **separates the program's logical memory from the physical RAM**. This allows a program to be *larger than the actual physical memory* available.

- **Core Idea:**
  
  - The OS keeps only the *actively used* parts (pages or segments) of a program in the main memory (RAM).
  
  - The *entire* program (all its pages) is stored on a fast disk (like an SSD) in a special area called the **swap space** or **paging file**.
  
  - When the program tries to access a part that is *not* in RAM, the OS automatically loads it from the disk, first swapping out an unused part from RAM if necessary.

- **Benefits:**
  
  1. **Programs can be larger than RAM:** A 50GB video editing program can run on a laptop with 16GB of RAM.
  
  2. **Increased Multiprogramming:** More processes can be in a "running" state because each one only takes up a small amount of *actual* RAM.
  
  3. **Faster Startup:** A program can start running as soon as its first page is loaded, rather than waiting for the entire program.

Virtual memory is typically implemented using **Demand Paging**.

## 8. Demand Paging

Demand Paging is the specific implementation of virtual memory that uses the paging hardware.

- **Concept:** Pages are only loaded from the disk into a memory frame "on demand," i.e., when they are accessed for the first time. This is also called a **lazy swapper**.

- **Page Table with Valid-Invalid Bit:**
  
  - To support this, each entry in the Page Table has an extra bit:
  
  - **Valid (v):** The page is **in RAM** (physical memory) and the frame mapping is correct.
  
  - **Invalid (i):** The page is **not in RAM** (it's either on the swap disk or is not a valid part of the program at all).

## 9. Page Fault

A **Page Fault** is the *mechanism* that makes demand paging work. It is **not an error**, but rather a hardware trap (an interrupt) to the operating system.

- **When does it happen?** A page fault occurs when the CPU tries to access a logical address, and the MMU looks at the Page Table and finds that the entry for that page is marked **INVALID**.

- **How the OS Handles a Page Fault (Step-by-Step):**
  
  1. The MMU triggers a **page fault trap** to the OS.
  
  2. The OS (in its trap handler) pauses the process.
  
  3. The OS checks if the access was valid (i.e., is the page on the swap disk, or was it a true error like a `NULL` pointer?).
  
  4. If it was a true error, the OS terminates the program (e.g., "Segmentation Fault").
  
  5. If the page is valid but just on disk, the OS must bring it into RAM:
     a. Find a free frame in physical memory.
     b. If there are no free frames, the OS must run a Page Replacement Algorithm (see next section) to select a "victim" frame.
     c. If the "victim" frame is "dirty" (i.e., it was modified, tracked by a **dirty bit**), the OS must write its contents back to the swap disk.
     d. The OS schedules a disk I/O operation to read the desired page from the swap disk into the new (free or victim) frame.
  
  6. This disk I/O is very slow. While it happens, the OS's CPU scheduler performs a **context switch** and lets another process run.
  
  7. Once the disk I/O is complete (signaled by a disk interrupt), the OS:
     a. Updates the Page Table for the original process. It sets the page's bit to VALID and stores the new frame number.
  
  8. The OS resumes the original process by **restarting the instruction** that caused the page fault in the first place. This time, the MMU finds a valid entry and the program continues, completely unaware that a page fault ever occurred.

- **Performance Impact:**
  
  - Page faults are very slow due to disk I/O.
  
  - **Effective Access Time (EAT):** `EAT = (1 – p) × (mem_access) + p × (page_fault_service_time)`
  
  - **Example:**
    
    - Memory Access Time: 200 nanoseconds
    
    - Page Fault Service Time: 8 milliseconds (8,000,000 ns)
    
    - If 1 out of 1,000 accesses is a page fault ($p = 0.001$):
      EAT = (0.999) × 200 + (0.001) × 8,000,000 = 199.8 + 8,000 = 8,199.8 ns
    
    - This is a slowdown factor of over 40! The page fault rate ($p$) must be kept *extremely* low.

## 10. Page Replacement Algorithms

When a page fault occurs and all frames are full, the OS must decide which page *currently in RAM* to "evict" or "swap out" to make room. The goal is to choose a page that is *least likely to be used soon*, to minimize future page faults.

- **Optimization:** A **modify bit (or dirty bit)** is used. If a page has not been modified (it is "clean"), it does not need to be written back to the disk; the new page can just overwrite it. This saves a disk I/O operation.

These algorithms are evaluated using a **reference string**, which is the sequence of pages a program accesses.

### Example Scenario

- **Reference String:** `7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 2`

- **Available Frames:** 3

### 1. First-In, First-Out (FIFO)

- **Algorithm:** Replaces the page that has been in memory the **longest** (the "oldest" page).

- **Implementation:** A simple queue.

- **Example (3 Frames):**
  
  - `7` -> [**7**] (Fault)
  
  - `0` -> [7, **0**] (Fault)
  
  - `1` -> [7, 0, **1**] (Fault)
  
  - `2` -> [**2**, 0, 1] (Fault, 7 is replaced)
  
  - `0` -> [2, 0, 1] (Hit)
  
  - `3` -> [2, **3**, 1] (Fault, 0 is replaced)
  
  - `0` -> [2, 3, **0**] (Fault, 1 is replaced)
  
  - `4` -> [**4**, 3, 0] (Fault, 2 is replaced)
  
  - `2` -> [4, **2**, 0] (Fault, 3 is replaced)
  
  - `3` -> [4, 2, **3**] (Fault, 0 is replaced)
  
  - `0` -> [**0**, 2, 3] (Fault, 4 is replaced)
  
  - `3` -> [0, 2, 3] (Hit)
  
  - `2` -> [0, 2, 3] (Hit)

- **Total Page Faults:** **10**

- **Con:** Poor performance. It may replace a critical, heavily-used page just because it was loaded early.

- **Belady's Anomaly:** A famous problem where **increasing the number of frames can sometimes** ***increase*** **the number of page faults** (which is counter-intuitive).

### 2. Optimal (OPT / MIN)

- **Algorithm:** Replaces the page that will **not be used for the longest period of time in the** ***future***.

- **Implementation:** Impossible in a real OS (it can't predict the future). It is used as a theoretical **benchmark** to measure how good other algorithms are.

- **Example (3 Frames):**
  
  - `7` -> [**7**] (Fault)
  
  - `0` -> [7, **0**] (Fault)
  
  - `1` -> [7, 0, **1**] (Fault)
  
  - `2` -> (Look at [7,0,1]. Future: `0, 3, 0, 4, 2...`. Page 0 is used soon. Page 2 is used. Page 1 and 7 are not used for a long time. Replace 7.) -> [**2**, 0, 1] (Fault)
  
  - `0` -> [2, 0, 1] (Hit)
  
  - `3` -> (Look at [2,0,1]. Future: `0, 4, 2, 3...`. Page 0 and 2 are used. Page 1 is not used again. Replace 1.) -> [2, 0, **3**] (Fault)
  
  - `0` -> [2, 0, 3] (Hit)
  
  - `4` -> (Look at [2,0,3]. Future: `2, 3, 0...`. All are used. 0 is furthest, then 3, then 2. Replace 0.) -> [2, **4**, 3] (Fault)
  
  - `2` -> [2, 4, 3] (Hit)
  
  - `3` -> [2, 4, 3] (Hit)
  
  - `0` -> (Look at [2,4,3]. Future: `3, 2...`. Page 2 and 3 are used. Page 4 is not. Replace 4.) -> [2, **0**, 3] (Fault)
  
  - `3` -> [2, 0, 3] (Hit)
  
  - `2` -> [2, 0, 3] (Hit)

- **Total Page Faults:** **7** (This is the best possible result for this string and frame count).

### 3. Least Recently Used (LRU)

- **Algorithm:** An approximation of OPT. Instead of looking at the future, it looks at the **past**. It replaces the page that has **not been used for the longest period of time**.

- **Example (3 Frames):**
  
  - `7` -> [**7**] (Fault) | Stack: 7
  
  - `0` -> [7, **0**] (Fault) | Stack: 7, 0
  
  - `1` -> [7, 0, **1**] (Fault) | Stack: 7, 0, 1
  
  - `2` -> (LRU is 7) -> [**2**, 0, 1] (Fault) | Stack: 0, 1, 2
  
  - `0` -> [2, **0**, 1] (Hit) | Stack: 1, 2, 0
  
  - `3` -> (LRU is 1) -> [2, 0, **3**] (Fault) | Stack: 2, 0, 3
  
  - `0` -> [2, **0**, 3] (Hit) | Stack: 2, 3, 0
  
  - `4` -> (LRU is 2) -> [**4**, 0, 3] (Fault) | Stack: 3, 0, 4
  
  - `2` -> (LRU is 3) -> [4, 0, **2**] (Fault) | Stack: 0, 4, 2
  
  - `3` -> (LRU is 0) -> [4, **3**, 2] (Fault) | Stack: 4, 2, 3
  
  - `0` -> (LRU is 4) -> [**0**, 3, 2] (Fault) | Stack: 2, 3, 0
  
  - `3` -> [0, **3**, 2] (Hit) | Stack: 2, 0, 3
  
  - `2` -> [0, 3, **2**] (Hit) | Stack: 0, 3, 2

- **Total Page Faults:** **9**

- **Pro:** Very good performance, does not suffer from Belady's Anomaly.

- **Con:** Hardware support is needed to make it efficient.

- **Implementation:**
  
  1. **Counters:** Each page entry has a counter. On reference, the CPU clock time is copied to the counter. To replace, the OS searches for the page with the *smallest* counter (time). This is slow.
  
  2. **Stack:** Keep a stack (e.g., a doubly-linked list) of page numbers. On reference, move that page to the top. The page at the bottom is always the LRU. This has no search cost but is expensive to update.

## 11. Allocation of Frames

This concept defines the *scope* of the page replacement algorithm and how many frames each process gets.

- **Minimum Frames:** Each process needs a *minimum* number of frames to run. This is defined by the computer's architecture (e.g., an instruction might need to access multiple pages at once).

- **Local Allocation:**
  
  - Each process is allocated a **fixed number** of frames (e.g., via fixed or priority allocation).
  
  - When a process page faults, it can *only* replace one of **its own** frames.
  
  - **Pro:** More predictable. One misbehaving, thrashing process cannot steal frames from other, well-behaved processes.
  
  - **Con:** Inefficient. A low-priority process might hold onto unused frames while a high-priority process is starving for memory.

- **Global Allocation:**
  
  - All frames in memory are in a **single global pool**, shared by all processes.
  
  - When a process page faults, the replacement algorithm can replace *any* frame in memory, typically one from a lower-priority process or one that is LRU *globally*.
  
  - **Pro:** More flexible and efficient. The OS can dynamically adjust memory allocation based on which processes *need* it most.
  
  - **Con:** Less predictable. A process's page fault rate now depends on the behavior of *all other* processes in the system.

## 12. Thrashing

**Thrashing** is a critical system-wide problem where the OS is spending **more time swapping pages** (paging) than it is spending on **actual execution**.

- **Symptom:** The system becomes extremely slow, disk I/O is at 100%, and the CPU is busy (running the OS paging code) but no real work (user processes) gets done.

- **Cause:**
  
  1. A process is given **too few frames** to hold its **working set**. The **working set** is the set of pages a process is *actively using* in a given time window.
  
  2. For example, a loop might span two pages (A and B). If the process is only given *one* frame, it will access Page A (page fault), then Page B (page fault, replaces A), then Page A (page fault, replaces B), and so on, causing a page fault on *every single instruction*.

- **The Thrashing Cycle (Global Allocation):**
  
  1. Process A needs more frames and starts thrashing.
  
  2. The OS (CPU scheduler) sees that Process A is always "waiting for I/O" (the disk).
  
  3. The OS thinks the CPU is underutilized (since Process A is waiting).
  
  4. The OS's long-term scheduler decides to **increase the degree of multiprogramming** by loading *another* process (Process B) into memory.
  
  5. This new Process B *steals* frames from Process A (and others).
  
  6. Process A now has *even fewer* frames and thrashes *even more*.
  
  7. This creates a disastrous feedback loop where CPU utilization plummets to near zero, and the system grinds to a halt.

- **Solution to Thrashing:**
  
  - **Working-Set Model:** The OS must monitor the working set (the active pages) of each process. It should **not** load a process into memory *unless* there are enough free frames to hold its entire current working set.
  
  - **Page-Fault Frequency (PFF):** The OS monitors the *rate* of page faults for each process.
    
    - If `PFF > Upper_Limit` (thrashing): The process needs *more* frames.
    
    - If `PFF < Lower_Limit` (too many frames): The process has more frames than it needs, and one can be taken away.
